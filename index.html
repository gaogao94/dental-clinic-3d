做了什么

一套 351 件牙科诊所 3D 资产库、一个平台化 3D 配置器、一套出图 / 算量 / 报价引擎。三件东西串成一条链：配置 → 出图 → 报价，交付物是 DXF 与 CSV，不是渲染图。

怎么做

Lux3D 是资产生产线的唯一来源：image-to-3D 批量生成 → 五轮质检与两轮返工 → 轻量化与尺寸标定 → three.js 组装成场景 → CAD 与报价引擎把场景变成图和钱。

01

复制的一致性，才是瓶颈

一家口腔诊所不大：90–240㎡、7–14 个房间、88–197 件家具设备、34 个机电点位。第十家店做得和第一家一样好，才是难点。

口腔诊所是标准化与差异化同时极高的空间。标准化在于：诊疗室永远需要牙椅、边柜、洗手台、医废桶；消毒室永远需要清洗、灭菌、干燥、封口四件事。差异化在于：社区店、儿童店、正畸、种植、美学，房间组合与设备等级完全不同。

行业里的现实做法是一店一设计：平面、设备、点位、算量、报价，全部重来一遍。连锁越扩张，设计产能越吃紧；一致性靠资深设计师盯，人一走，标准就散。于是成本结构变得反直觉：多开一家店，贵在设计要重做一遍。

我们的判断是，可复用的东西有三层，都能写成数据：空间的硬点带宽、房间与设备的配置规则、可被反复引用的 3D 资产。这三层一旦成立，配一家诊所就从「从零设计」变成「一次参数选择」。

这也是我们选择口腔诊所而不是泛商业空间的原因：它的房间类型、设备清单与机电要求都收敛，足够窄，才可能被平台化。

我们要验证的是一套 AI 生成的资产能不能撑起一家诊所从配置、出图到报价的完整交付。生成一个好看的牙椅，离这条链还差得远。
02

把汽车平台的方法，搬进诊所

汽车工业没有停在把一辆车做得更好，它让同一套硬点与接口长出很多车型：冻结硬点 → 标准接口 → 通用化分层 → 规模覆盖 → 复用验证。

但这套方法不能照抄。汽车的平台是「算力与硬件的归组」，降本靠 BOM 通用件；医院与诊所的域是「责任、流程与数据的归组」，降本只能靠交付复用，同一份图纸逻辑、同一套房间模板、同一批资产，在不同门店里被反复调用（见项目研究底稿：汽车平台 → 医疗平台的域架构分析）。所以我们只取方法，不取形式：不设域控制器，只冻结空间与机电的硬点。

三层变量：配一家诊所 = 选不变量 + 选受限变量 + 调自由量

  • 不变量 · 平台带宽：S 90㎡·2 椅·1 槽位 / M 150㎡·4 椅·2 槽位 / L 240㎡·6 椅·3 槽位。这是「硬点」，不允许在配置时被破坏。
  • 受限变量 · 门店类型：社区家庭、儿童诊疗、正畸中心、种植旗舰、美学体验。每类店有自己的必含房间、设备等级与差异件清单，且受平台档位约束（S 档开不出种植旗舰）。

这套分层带来的直接结果，是「复用」第一次可以被计量：在一套 L 档美学体验店的配置里，平台件 143 件、差异件 55 件，平台件类型复用率 53%。这个数字比任何「降本」话术都更接近采购方关心的问题：这套设计里有多少可以复制。

04

Lux3D 是承重墙

351 件、2 小时 36 分、652 积分。这个规模的诊所资产库，过去意味着数月的外包建模；Lux3D 让它在一天之内成立。但工作量的大头在让生成结果可用。

资产是这个平台的地基：没有资产，配置器只是一个空房间；没有 351 件的「量」，就谈不上平台件、差异件与复用率。所以 Lux3D 在这件作品里是唯一的资产来源，库里每一件 GLB 都由它生成，没有一件是买来或手工建的。

生成走的是 OpenAPI + 官方计费链路：每一次提交前先做一次滚动报价（quote），报价 5 分钟过期；每次创建任务绑定一个未过期的 quote；任务完成后立即下载，输出链接只有 2 小时有效期。整条链路留下三类可复核的落盘证据：报价记录、任务记录、平台回执。

四条工程决策

  • 最便宜路线优先，先覆盖「量」。全库统一 G1-Turbo（图生 3D 1 积分/件），只在没有可用参考图时才走文生 3D（77 次，单价更高）。先用最低成本把 13 类空间铺满，再把预算花在返工上。
  • 滚动报价 + 预算台账。37 组报价，每一组都记录 quoteId、金额、余额与过期时间；预算写入台账（授权 3,200 / 已用 652 / 余额 2,548）。任何一次「超预算」都会在提交前被拦住。
  • 即下即存 + 断点续跑。输出链接 2 小时过期，所以下载与提交解耦；失败件进入重试队列（--retry-failed），进程中断也不会重复计费。
  • 5 并发，不追求极限。官方免费档的并发上限是 5。压满会比「更快的失败」更慢，因为限流重试会把整组报价拖过期。

成本为什么重要

一个平台的最小可行资产库，是覆盖所有空间类型的全量清单。缺一张消毒室的工作台，那一间就配不出来。用最便宜的档位把 351 件铺满、再对 33 件返工，比一开始用 10 倍单价生成 35 件精品更接近可用。这套「先全量、后返工」的预算分配，是这次能在 652 积分内交付出一个完整库的直接原因。

05

33 次返工，换来 0 坏件

AI 生成的失败模式很固定：碎片漂浮、多件粘连、尺度离谱、朝向相反。质检要在入库之前把不合格的拦下来。

我们没有「生成完就收货」。每一轮批量作业结束后，用无头浏览器把新完成的模型渲染成 320px 缩略图（本机没有 GPU，走软件渲染也可跑），逐件看三件事：能不能看出是什么、画面里是不是只有这一件、比例与朝向是否合理。不合格的进返工队列，重写提示词后重新生成，再复核。

五轮下来，坏件数先从 2 涨到 14、再到 26，然后被压回 5、最后归零。曲线上升，是因为每一轮都在扩大检查面：27 件时只发现 2 个问题，不代表质量好，只代表看得少。

返工是怎么发生的

返工前先要把问题写清楚。每一件坏件都会先被写成一句可执行的问题描述，再改写对应的生成提示词：是主体不明确，就补主体与视角；是多件粘连，就明确「single object, isolated」；是尺度离谱，就在清单的 note 里补真实尺寸再生成。两轮返工共 33 件（第一轮 28 件、第二轮 5 件）：26 件在第 3 轮直接复核通过，其余 7 件在第 4 轮抽查中全部通过。

尺寸与朝向：让生成的模型能进平面图

生成件只有形体，没有「这是 2.4 米」这种知识。如果直接摆进场景，牙椅会和沙发一样高，平面图上的家具会互相穿模。所以我们补了两件事。平面尺寸实测是用无头 Chrome 逐件渲染、读归一化后的世界包围盒、按 rotY 转正，实测了 119 件资产的平面占位，写进 demo/js/footprint.js；朝向与基准是为牙椅、前台、沙发、工作台等关键件标定正面朝向与落地基准（demo/data/asset-tuning.json）。这张标定表，是 3D 场景能直接长出 1:50 平面图的前提。

至于「AI 生成件到底有多大」这件事，我们给的是可核对的口径，不用「比例正确」四个字带过：每件在清单里都写了参考尺寸（note 字段），场景基准与实测 footprint 两套数据同时存在，出图用的是实测值，人工核对时看的是参考尺寸。

体量：从 9.9MB 到 0.75MB

原始生成件平均 9.9 MB（2K 贴图、未压缩），一个 197 件家具的配置要下载近 2GB，网页里跑不动。我们做了两级轻量化：交付件降到 1.95 MB（1024 JPEG + 几何量化），演示用 LOD 再降到 0.75 MB（meshopt 简化 + 512 贴图）。单件体积下降 92%，全库从 3.48 GB 降到 113 MB。

产品层迭代：提交前最后一小时

资产质量之外，配置器本身也经过一轮肉眼可见的修正。下面是同一个配置（M 档 · 社区家庭店 · 150㎡ · 4 椅）在两个时间点的画面：左边是 17:19 的首版，右边是 18:05 的版本。

图 6-7三处差异都值得记：加载从卡在 34/70 变成一次加载完成；家具数从 135 收敛到 113，是布局去重与房间模板修正的结果；复用率从 99% 修正到 53%。按实际使用到的资产类型去重统计后，这个数字才回答了「有多少是可以复制的」。同一天里，配置器还补上了造价与工时的指标卡：配置器不再只是「看」，开始「算」。

07

像配车一样配诊所

左边是车型，上边是平台，下边是内饰，右边是这台「车」的配置单与指标。改任何一个，3D 场景、房间清单、复用率与组合数同时变。

能改什么

  • 平台档位：S / M / L 三档，决定面积、开间进深、诊室数、椅位与模块槽位。降到放不下的档位时，门店类型与模块会自动禁用。
  • 门店类型：5 类，决定必含房间、牙椅等级与差异件清单（儿童椅、正畸椅、种植椅、高端椅；CBCT、铅防护、咖啡吧、儿童角）。
  • 选装模块：影像室、技工室、儿童区、咨询室、咖啡吧、消毒升级；模块槽位 1 / 2 / 3，超槽位直接禁用，不会悄悄叠加。
  • 风格：5 套墙地木作与灯光色温，切换时软装变体同步替换，但不改变硬点与设备。
  • 视角：总览 / 前台 / 候诊 / 诊疗 / 消毒，相机 600ms 飞入；点房间标签也能飞。
  • 两个视图：硬点、平台件 / 差异件描边；另有一个天花开关，程序化生成 LED 平板灯与空调风口。

指标面板回答什么

面积、诊室、椅位、房间数是配置的「物理结果」；平台件复用率是配置的「经济结果」；衍生组合数是平台的「规模上限」。右下角的配置清单按房间分组列出家具件数，它是出图与算量的直接输入，不另算一遍。

怎么做到在无 GPU 的机器上能跑

three.js 与全部依赖本地化，没有任何 CDN；建筑壳体（地面、2.8m 墙、门洞、玻璃隔断）由程序生成，不占模型体积；同一资产在场景里只加载一次、其余 clone；只加载当前配置用得到的资产（约 50–70 个），并按需渲染。本机没有显卡、走 SwiftShader 软件渲染也能完成截图与交互验证；真实 GPU 下的目标是 45 fps 以上。

部署：不让页面依赖一张会过期的签名链接

演示站由自托管服务器提供（Node ≥ 18，零依赖，只用内置模块）：浏览器请求模型时，服务器用 OSS 凭据去对象存储取，首次落盘缓存，之后本地命中（实测 3–12 ms / 件）。这样做的三个结果：页面同源、没有 CORS、没有签名 URL 过期；对象桶保持私有，不需要开 public-read；页面永远不因为链接过期而失效。这是「评审任何时候点开都能用」的技术前提。

维护上也有据可查：提交 48188eb 修掉了缓存导致的空房间与前台布局问题；3629c0b 把出图与报价接进演示页；b63beb8 落地了自托管服务器包。作品留成了一条能继续往前走的分支。

别人能拿走什么

  • 清单与目录：inventory.json 的字段结构（id / 中英文名 / 分类 / 优先级 / 检索词 / 生成提示词 / 参考尺寸）可以直接换成另一个行业。
  • 单价与工效：price-book.js 是数据文件，商务可以改数而不碰公式；出图与报价的接口契约写在 source/drawing-quote-contract.md。
  • 生成与质检脚本：批量生成、滚动报价、即下即存、缩略图质检，这一套与行业无关，换清单即可复用。
  • 交付包：lux3d-delivery.json + 内嵌预览页，是 Lux3D 体系里可直接交付的形态。
10

我们没做的，和不敢说的

评审看的是可信度。所以这一节只写限制，不写愿景。

六条边界

1 · 资产精度。351 件由 G1-Turbo（1 积分/件）生成，形体与贴图整体可用，但局部细节与真实产品的比例不保证一致。清单 note 里的尺寸是可核对的参考值，不是产品参数表；要用于工程设计与施工，必须按实物核对。

2 · 出图定位。这是方案阶段的平面布置图与机电点位图：A2、1:50 / 1:100、DXF R2007，可作 CAD 二次设计的底图，不是结构图、节点图或施工图。

3 · 报价口径。造价是估算，含税、±8% 区间；单价与工效来自 demo/js/price-book.js 的假设，不是投标价。工期是净施工工期，不含设备采购与报建审批。

4 · 7 件边界件。imaging-positioning-chair、intraoral-camera、shoe-change-bench、emergency-exit-sign、digital-signage-kiosk、dental-computer-tower、corridor-handrail 可用但不完美，已在第 5 章逐件说明。

5 · 场景是程序化摆放。房间与家具由布局算法生成，不是对真实建筑的测绘；开间、机电、给排水需按实际条件与规范深化。天花 GLB 件因体积与姿态问题没有放进 3D 场景，天花以程序化灯具与风口代替。

6 · 没覆盖的部分。结构、暖通负荷计算、消防报审、设备品牌选型、软装深化，都不在本作品范围内；演示页在无 GPU 的机器上以软件渲染验证，真实 GPU 帧率未实测（目标 45 fps 以上）。

把这些写出来，是因为边界本身就是交付物的一部分：一个设计工具如果不说清「图能用到哪一步」，它就在把风险转嫁给使用者。我们更愿意让评委看到：哪些数字是实测的（119 件 footprint、1,595 组校验、351 件全检），哪些是假设的（单价、工效、风格系数）。
